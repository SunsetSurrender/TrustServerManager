Scopo

Il documento descrive l'installazione di produzione di Trust Server Manager (TSM) e il suo utilizzo. La Parte I è rivolta a chi amministra il server; la Parte II a chi usa l'applicazione.

Parte I

Manuale tecnico

Server, componenti, sicurezza, aggiornamenti, backup e monitoraggio.

1Architettura

TSM è un'applicazione web interna per la gestione delle sale server: siti, sale, rack e dispositivi installati, con le relative scadenze di garanzia e supporto. Gira su una sola macchina virtuale come insieme di container Docker, avviati da systemd.

Figura 1. Componenti e flussi. Solo il componente web pubblica porte verso l'esterno.
ServizioFunzioneRetiUtente
webServe l'interfaccia, termina TLS e inoltra le chiamate /api. Pubblica le porte 80 (reindirizzamento) e 443.edge, internaluid 101
apiAutenticazione, inventario, ricerche, foto, impostazioni e registro delle modifiche.edge, internaluid 10001
workerInvio degli avvisi di scadenza e pulizia delle foto non più referenziate. Ne è attiva una sola istanza.internaluid 10001
dbDatabase PostgreSQL 17, con i dati sul disco dedicato.internaluid 70
migrateAllinea lo schema del database e imposta le password dei ruoli, quindi termina.internaluid 10001

I container girano con filesystem in sola lettura, senza capability aggiuntive e con l'opzione no-new-privileges. Le immagini sono identificate per digest; il file deploy/release.pin riporta quelle del rilascio installato.

/opt/tsm contiene solo il pacchetto di rilascio prodotto da tools/release-bundle.sh: non è un repository git e non contiene file di sviluppo. Segreti, certificato e .env vengono creati sul server e non fanno parte del pacchetto.

4Gestione del servizio

Il servizio è l'unità systemd tsm.service, abilitata all'avvio. Alla partenza systemd attende il montaggio di /srv/tsm-data, esegue il preflight e avvia i container con docker compose up -d. Lo stato atteso è active (exited).

Comandi principali

# stato
systemctl status tsm.service --no-pager
docker compose ps                         # db, api, web, worker e backup devono risultare healthy

# arresto, avvio, riavvio
systemctl stop tsm.service
systemctl start tsm.service
systemctl restart tsm.service

# log
journalctl -u tsm.service -n 50 --no-pager
docker compose logs --tail 100 api        # oppure web, worker, db

# disponibilità dell'applicazione
curl -sk https://10.11.43.230/api/ready

Riavvio automatico

L'unità non viene riavviata automaticamente in caso di errore (Restart=no): un rifiuto del preflight indica una causa strutturale, come il disco dati assente o il certificato mancante, che va risolta prima di riprovare. I singoli container si riavviano invece autonomamente (restart: unless-stopped).

Preflight

Il controllo deploy/preflight.sh --dir /opt/tsm può essere eseguito manualmente in qualsiasi momento e non modifica nulla. Termina con codice 0 se tutti i requisiti sono soddisfatti; in caso contrario il codice indica il requisito mancante (paragrafo 9.3).

5Sicurezza

Esposizione

  • Sono pubblicate solo le porte 80, che reindirizza su HTTPS, e 443. API e database non sono raggiungibili dall'esterno.
  • Il cookie di sessione è Secure e SameSite=Strict; in produzione l'applicazione non si avvia con impostazioni diverse.
  • Le richieste che modificano dati sono accettate solo dall'origine configurata in TSM_PUBLIC_ORIGIN.

Ruoli del database

RuoloUtilizzato daPrivilegi
tsmmigrate, manutenzioneProprietario dello schema
tsm_apiapiLettura e inserimento; lo storico dell'inventario non è modificabile
tsm_workerworkerCome tsm_api, più la cancellazione delle foto non referenziate

Le password sono montate come secret Docker e non come variabili d'ambiente, quindi non compaiono in docker inspect né nei log.

Uscita per inattività

Una sessione senza richieste per più dei minuti impostati in «Sicurezza accessi» (60 in modo predefinito; 0 la disattiva, altrimenti fra 15 e 720) viene chiusa dal server e revocata; il browser torna da solo alla schermata di accesso con il motivo. Resta comunque la durata massima di 12 ore.

Blocco dell'utenza dopo accessi falliti

Dopo un numero di accessi falliti consecutivi (5 in modo predefinito, impostabile fra 3 e 20 dagli amministratori in Impostazioni, scheda «Sicurezza accessi») l'utenza viene bloccata. Il blocco non scade: un'utenza bloccata non entra nemmeno con la password corretta finché un amministratore non la sblocca con il pulsante «Sblocca». Anche la reimpostazione della password e la riattivazione sbloccano l'utenza. Blocco, sblocco e cambio di soglia sono registrati nel registro di audit.

Se l'unico amministratore è bloccato, lo sblocco si esegue dal server:

cd /opt/tsm
docker compose run --rm migrate python scripts/unlock_user.py <utenza>

Resta inoltre un limite per indirizzo IP (100 tentativi falliti in 15 minuti) contro i tentativi in massa. Poiché tutti accedono dal web gateway il limite è condiviso, per questo è volutamente alto.

Conservazione dei dati di accesso

Ogni notte alle 03:45 il worker cancella i tentativi di accesso, le sessioni chiuse e i codici di recupero più vecchi di 90 giorni (TSM_AUTH_RETENTION_DAYS in .env, minimo 30). Il registro di audit non viene toccato: accessi falliti, blocchi e recuperi restano lì. Ogni giro lascia una riga in maintenance_runs e, se ha cancellato qualcosa, una riga di audit con i conteggi.

Log dei container

Ogni container tiene al massimo 5 file di log da 10 MB, ruotati da Docker (compose.yaml, dalla 0.4.2). Il predefinito del demone Docker e il tetto al journal di sistema sono lato sistemistico, in ops/README.md.

Recupero della password via email

Dalla schermata di accesso, «Password dimenticata?» invia all'indirizzo registrato sull'utenza un codice di 12 caratteri (ABCD-EFGH-JKMN) e un link che compila già utenza e codice. Il codice vale 30 minuti, si usa una volta e dopo 5 tentativi errati decade; una nuova richiesta annulla la precedente, con un massimo di 3 richieste all'ora per utenza. Nel database resta solo l'hash del codice.

  • La risposta alla richiesta è sempre la stessa, che l'utenza esista o no: il modulo non permette di scoprire quali utenze esistono. L'esito reale (inviato, utenza inesistente, senza email, bloccata…) è nel registro di audit.
  • Il recupero non sblocca un'utenza bloccata per accessi falliti: lo sblocco resta riservato agli amministratori.
  • Funziona solo con la posta configurata (paragrafo 6) e per le utenze con un indirizzo email; gli amministratori possono disattivarlo nella scheda «Sicurezza accessi».
  • Poiché l'applicazione si raggiunge dal web gateway, il link della mail spesso non si apre dove la mail viene letta: in quel caso si usa «Ho un codice» e si ricopia il codice.

Certificato TLS

Il certificato è emesso da una CA interna creata con deploy/make-internal-tls.sh. Riporta l'indirizzo 10.11.43.230 e il nome tsm-prd, ha validità di 825 giorni e scade il 28 gennaio 2029. Il certificato della CA (secrets/tls/ca-interna.crt) è installato sul web gateway tra le autorità di certificazione radice attendibili.

# rinnovo con la stessa CA: sul gateway non serve alcuna modifica
bash deploy/make-internal-tls.sh --ip 10.11.43.230 --name tsm-prd --force
docker compose restart web
  • La chiave della CA è in /root/tsm-ca e va conservata preferibilmente fuori dal server, riportandola solo per i rinnovi.
  • In caso di cambio di indirizzo IP si rigenera il certificato con il nuovo valore di --ip e si aggiorna TSM_PUBLIC_ORIGIN.
  • Per pubblicare il servizio anche con un nome DNS si aggiungono un parametro --name al certificato e la relativa origine in .env, separata da virgola.

6Configurazione

I parametri non riservati sono nel file /opt/tsm/.env, letto automaticamente da Docker Compose.

TSM_PUBLIC_ORIGIN=https://10.11.43.230
TSM_SMTP_HOST=legolas1,legolas2  # uno o più relay, provati in ordine
TSM_SMTP_PORT=25
TSM_SMTP_TLS_MODE=none           # starttls, tls oppure none (Legolas su 25: none)
TSM_SMTP_SENDER=t-servermanager@ittelecom.it
TSM_SMTP_USERNAME=               # vuoto: relay che accetta per indirizzo IP
  • La password SMTP si inserisce in secrets/smtp_password (permessi 0400, uid 10001), non in .env.
  • TSM_ENV e TSM_COOKIE_SECURE non vanno impostati: i valori predefiniti sono quelli di produzione e un valore diverso blocca l'avvio (codice 40).

Posta elettronica

Dall'applicazione si configurano destinatari, anticipo e orario degli avvisi. Server, porta, cifratura, mittente e credenziali del relay si configurano esclusivamente nel file .env. Dopo una modifica:

docker compose up -d api worker

La configurazione si verifica con il pulsante «Invia messaggio di prova» in Impostazioni, scheda Notifiche (al massimo 3 prove all'ora per utente).

  • Più relay. Con più nomi in TSM_SMTP_HOST si passa al successivo solo se il precedente non risponde; un rifiuto (destinatario, mittente, cifratura) non fa cambiare relay, perché gli altri risponderebbero allo stesso modo.
  • Rete. Le email partono dai container verso il relay con l'indirizzo della VM: non serve pubblicare porte né installare Postfix. Gli avvisi di scadenza partono dal worker, che dalla 0.4.3 ha una rete di sola uscita (egress).
  • Messaggi. Ogni email ha un corpo HTML con il logo incorporato e un corpo di solo testo equivalente, per i client che non mostrano l'HTML.

7Aggiornamento

Il server non accede a internet. Ogni rilascio viene preparato sulla postazione di sviluppo come pacchetto comprensivo delle immagini Docker (tsm-images.tar) e trasferito sul server. L'aggiornamento non modifica dati, utenze, segreti, certificato e .env.

Preparazione del pacchetto

bash tools/build-release.sh
git add deploy/release.pin
git commit -m "release: pin <commit>"
bash tools/release-bundle.sh --out <cartella> --with-images

Installazione su tsm-prd

  1. Copiare il contenuto del pacchetto in /opt/tsm, sovrascrivendo i file esistenti.
  2. Ripristinare i permessi di esecuzione: chmod 0750 deploy/*.sh accettazione/*.sh.
  3. Verificare il pacchetto: bash accettazione/release-bundle.sh --verify /opt/tsm.
  4. Caricare le immagini: docker load -i tsm-images.tar, quindi eliminare il file.
  5. Eseguire il preflight: bash deploy/preflight.sh --dir /opt/tsm.
  6. Riavviare il servizio: systemctl restart tsm.service. Le eventuali migrazioni dello schema vengono applicate automaticamente.
  7. Controllare lo stato con docker compose ps e verificare l'interfaccia dal web gateway.

Ogni rilascio ha un tag distinto (0.3.1, 0.4.0 e successivi). Dopo la verifica le immagini precedenti si rimuovono con docker rmi tsm-api:<versione> tsm-web:<versione>.

8Backup e ripristino

Il backup è eseguito a livello di macchina virtuale con Veeam, a cura del gruppo che gestisce i backup. Requisiti per TSM:

  • il job deve includere entrambi i dischi, senza esclusioni;
  • il ripristino deve essere provato almeno una volta, verificando che il disco dati sia montato e che l'applicazione riparta con i propri dati;
  • /var/lib/docker non contiene dati applicativi: le immagini si ricaricano dal pacchetto di rilascio.

Dump notturno del database

Dalla 0.4.2 il servizio backup scrive ogni notte alle 02:15 un dump completo del database in /srv/tsm-data/backups (formato pg_dump -Fc, file tsm-AAAAMMGG-HHMMSS.dump, permessi 0600) e conserva gli ultimi 14. Il file prende il nome definitivo solo dopo essere stato riletto per intero. Esito, dimensione e spazio libero del disco dati sono visibili nella pagina «Stato del sistema» e controllati da check_tsm_maintenance. Orario e numero di copie si cambiano in .env (TSM_DUMP_HOUR, TSM_DUMP_MINUTE, TSM_DUMP_KEEP).

Il dump non sostituisce Veeam: Veeam salva la macchina, il dump è una copia sicuramente coerente del solo database, ripristinabile anche su un'altra installazione. Un dump si può lanciare a mano prima di un intervento:

docker compose exec backup sh /opt/tsm-backup/backup.sh --now

Ripristino da un dump

# 1. fermare il ripristino automatico e i servizi che scrivono
systemctl stop tsm-autoheal.timer
cd /opt/tsm
docker compose stop api worker web backup
# 2. ripristinare (sostituisce il contenuto attuale del database)
ls -lt /srv/tsm-data/backups | head
docker compose cp /srv/tsm-data/backups/tsm-AAAAMMGG-HHMMSS.dump db:/tmp/r.dump
docker compose exec -T db pg_restore -U tsm -d tsm --clean --if-exists --single-transaction /tmp/r.dump
docker compose exec -T db rm /tmp/r.dump
# 3. ripartire (le migrazioni si riapplicano se il dump è di una versione precedente)
systemctl restart tsm.service
systemctl start tsm-autoheal.timer

Con --single-transaction il ripristino è tutto o niente: se fallisce, il database resta com'era. Le modifiche successive al dump vanno perse.

Verifiche dopo un ripristino

findmnt -M /srv/tsm-data
bash deploy/preflight.sh --dir /opt/tsm
systemctl restart tsm.service
docker compose ps
docker compose run --rm migrate python scripts/project.py --verify

Esportazione logica

Un amministratore può esportare dall'applicazione il JSON completo (struttura, inventario e registro). È consigliato prima di interventi rilevanti.

9Monitoraggio e diagnostica

NOTA

Monitoraggio, integrità dei file e ripristino automatico sono attività sistemistiche: i relativi file stanno nella cartella ops/ del repository, documentata in ops/README.md, non fanno parte del pacchetto di rilascio e un aggiornamento dell'applicazione non li modifica.

Percorsi monitorati

10Introduzione

TSM descrive le sale server dell'azienda: la posizione di ogni rack, i dispositivi installati, lo spazio disponibile e le scadenze di garanzie e contratti di supporto.

Figura 2. Organizzazione dei dati. All'installazione sono presenti 3 siti, 6 sale e 102 rack, senza dispositivi.

La struttura iniziale (siti, sale con la relativa pianta, rack con nome, fila, altezza e numeri di inventario) è stata caricata all'installazione. I dispositivi si inseriscono dall'applicazione, singolarmente o tramite il modello Excel (capitolo 16).

Ogni modifica genera una nuova versione dell'inventario e una voce nel registro, con autore e data. Le versioni precedenti restano conservate.

11Accesso e privilegi

L'applicazione si apre all'indirizzo https://10.11.43.230 dal browser del web gateway. Sono supportati Firefox, Chrome ed Edge. Al primo accesso con una password provvisoria l'applicazione ne richiede la sostituzione, senza chiedere di ridigitare la provvisoria appena usata; la nuova password va scritta due volte e deve avere almeno 12 caratteri e può contenere spazi. Sotto il campo un indicatore ne valuta la robustezza (non sicura, debole, accettabile, sicura): conta soprattutto la lunghezza, e una frase di quattro o cinque parole è la scelta migliore. La versione dell'applicazione è indicata nella schermata di accesso e nella barra superiore.

16Importazione ed esportazione

Modello Excel

Il file «Modello dispositivi sale.xlsx» consente di caricare i dispositivi in blocco. Si compila il primo foglio, «Dispositivi»:

  1. si seleziona la sala; l'elenco dei rack mostra solo quelli della sala scelta e il sito viene compilato automaticamente;
  2. sala, rack e nome sono obbligatori; tipo, stato, unità e altezza sono raccomandati; le date si scrivono nel formato 2027-12-31;
  3. la colonna _uid resta vuota;
  4. in modalità Editing si sceglie «Importa dati» e si seleziona il file. L'anteprima riporta per ogni riga l'esito (nuovo, aggiornato o scartato) e il motivo; l'importazione si conferma dopo averla verificata.

L'importazione può avvenire in più riprese, per esempio una sala alla volta. Nel foglio sono evidenziate in rosso le righe con dispositivi che eccedono l'altezza del rack.

Seriali dei rack

I seriali dei rack si caricano dall'applicazione, in modalità Editing, dalla pagina Impostazioni, scheda «Importa / Esporta»:

  1. «Scarica foglio Seriali rack da compilare»: un file con una riga per ogni rack esistente e i seriali attuali;
  2. si compilano «seriale effettivo 1» e, se il rack ne ha due, «seriale effettivo 2». Le righe con entrambe le colonne vuote non cambiano il rack; NESSUNO nella prima colonna lo lascia senza seriali. La colonna _uid non va modificata;
  3. «Importa seriali rack (Excel)…»: l'anteprima elenca per ogni rack il prima e il dopo e le righe scartate con il motivo; «Applica import» salva, e la modifica è annullabile come le altre.

Si aggiornano solo i seriali di rack esistenti: posizione, dimensioni e struttura delle sale non cambiano. Rack e sale nuovi si creano in Editing, sulla pianta.

17Amministrazione

Utenze

  • Le utenze si creano da Impostazioni, scheda «Utenti e privilegi», indicando nome utenza e privilegio.
  • L'indirizzo email, facoltativo, serve al recupero della password: si imposta alla creazione o con «Modifica».
  • La password provvisoria è generata dal sistema (sei gruppi di cinque lettere minuscole e cifre, senza caratteri ambigui, facili da ridigitare dal web gateway) e mostrata una sola volta; va comunicata all'interessato, che la sostituisce al primo accesso. Le utenze in attesa sono contrassegnate come «pw provvisoria».
  • Le utenze non si cancellano ma si disattivano, in modo che il registro resti riconducibile agli autori delle modifiche.
  • Un'utenza bloccata per accessi falliti è contrassegnata come «bloccata»; il pulsante «Sblocca» la riabilita senza cambiarne la password.
  • «Reimposta password» offre due strade: «Genera provvisoria» oppure «Scegli tu la password», con la stessa politica delle altre password. Con la password scelta il cambio al primo accesso è attivo in modo predefinito; disattivarlo lascia una password nota all'amministratore e l'operazione è registrata.

Ruoli applicativi tsm_api e tsm_worker

Il servizio migrate imposta a ogni avvio le password dei ruoli applicativi leggendole dai file dei secret. La rotazione consiste quindi nella sostituzione del file e in un riavvio.

# esempio per tsm_api; per tsm_worker usare worker_db_password
cd /opt/tsm
cp -p secrets/api_db_password /root/api_db_password.prec      # copia per il ripristino
umask 077
openssl rand -base64 24 | tr -d '\n+/=' > /root/nuova
install -m 0400 -o 10001 -g 10001 /root/nuova secrets/api_db_password
shred -u /root/nuova
systemctl restart tsm.service
docker compose ps -a                         # migrate: Exited (0); gli altri healthy
docker compose logs migrate | grep "password del ruolo"

A verifica conclusa la copia precedente si elimina con shred -u /root/api_db_password.prec. Se migrate termina con errore, si ripristina la copia e si riavvia.

Ruolo proprietario tsm

La password del proprietario dello schema è impostata in PostgreSQL alla creazione del database e non viene riletta dal file. Va quindi modificata prima nel database e poi nel file, in quest'ordine: con il solo file aggiornato migrate non riesce ad autenticarsi e il servizio non si avvia.

cd /opt/tsm
cp -p secrets/postgres_password /root/postgres_password.prec
umask 077
openssl rand -base64 24 | tr -d '\n+/=' > /root/nuova
# 1. nel database (la password passa da stdin, non compare nella lista dei processi)
printf "ALTER ROLE tsm WITH PASSWORD '%s';\n" "$(cat /root/nuova)" \
  | docker compose exec -T db psql -U tsm -d tsm -q
# 2. nel file del secret
install -m 0400 -o 10001 -g 10001 /root/nuova secrets/postgres_password
shred -u /root/nuova
systemctl restart tsm.service
docker compose ps -a                         # migrate: Exited (0)

Relay SMTP

La password si cambia prima sul relay, a cura di chi lo gestisce, poi nel file:

cd /opt/tsm
umask 077
read -rs -p "Nuova password SMTP: " P; printf '%s' "$P" > /root/nuova; unset P
install -m 0400 -o 10001 -g 10001 /root/nuova secrets/smtp_password
shred -u /root/nuova
systemctl restart tsm.service

La password viene digitata senza eco e non resta nella cronologia della shell. Si verifica con l'invio di prova da Impostazioni, Notifiche.

CA interna

In caso di compromissione della chiave della CA si crea una nuova CA: si sposta /root/tsm-ca fuori dal server, si esegue deploy/make-internal-tls.sh --ip 10.11.43.230 --name tsm-prd --force, che genera una nuova CA e un nuovo certificato, si riavvia web e si sostituisce il certificato della CA installato sul web gateway.

Utenze dell'applicazione

Ogni utente cambia la propria password dal Profilo, oppure la recupera via email dalla schermata di accesso (paragrafo 5). Un amministratore può reimpostarla con una provvisoria generata o con una password scelta, e può disattivare un'utenza. In caso di perdita della password dell'unico amministratore si procede come indicato nel paragrafo 9.4.
